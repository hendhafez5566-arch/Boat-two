# قنوات الاتصال — دفعة المطابقة

فُتح Connect Account الحقيقي في BotSailor، ومقابله في Boat Two. لم يُضغط Disconnect أو Delete أو تفويض مزود أو إرسال حقيقي. القياسات من DOM/Computed Styles على1363×936 في channels-reference-metrics.json.

## الفرق والتنفيذ

كان Boat يعرض تعليمات تشغيل كبيرة وكل تفاصيل الحسابات والتشخيصات والتثبيت بصورة مفتوحة. أُضيف جدول بالحساب والحالة والمنصة وآخر فحص وMM والإجراءات، مع إحصاءات الإجمالي/متصل/ينتهي قريبًا/متوقف، وبحث وفلتري المنصة والحالة. «إدارة» يفتح التفاصيل التشغيلية الموجودة للحساب نفسه؛ روابط المدير والوارد والتشخيص والتوكين والتثبيت والإعدادات والحذف موجودة ولم تُحذف.

نُقلت تعليمات أول محادثة إلى دليل الربط القابل للفتح؛ وبطاقات الاتصالات المتاحة صارت بإطار مرجعي وبدون أشرطة الألوان الزائدة. مكوّن ChannelCatalog يستخدم mode خاص لهذه الصفحة، مع الحفاظ على عرضه الافتراضي في استخداماته الأخرى.

لا يساوي status=active اتصالًا موثوقًا. حالة «ينتهي قريبًا» تستعمل دليل API الموجود authorization_expiring فقط. الحساب المتوقف يتغلب على دليل اتصال قديم. البحث والحالات والفلاتر لا تغير أي سجل.

## نتائج الاختبارات وحدودها

- PASS: حالات verified/expiring/expired/disabled/unknown، تركيب فلاتر المنصة والحالة والاسم/المعرف، وعدم تغيير بيانات المصدر، وعرض كتالوجات المنصات الستة في النمطين.
- PASS:6/6 HTTP لإدارة القنوات على بيانات معزولة: إنشاء واسترجاع وتعديل وحالة متوقفة، رفض مدخلات غير صالحة قبل اتصال مزود، Owner/Admin/Agent وعزل الشركات؛ channels-http.json.
- PASS: TypeScript وESLint وبناء Web؛ سجل البناء في channels-build.txt.
- PASS:9/9 رحلات HTTP حقيقية معزولة عبر Nest/PGlite وschema104، تشمل create/save/reopen/preview/publish/republish وصلاحيات وعزل شركات وWebchat→CRM→Human Handoff وتراجع User Input Flow. الدليل channels-regression-http.json. لم يُعد بناء User Input Flow.
- فحص أسماء مسارات Channel API قبل/بعد يثبت بقاء تعبيراتها؛ لا يعد بديلًا لاختبار النقر.
- القبول التفاعلي والمرئي للكود المعدل ونشره: لم يُعتمدا في هذا checkpoint؛ لا PASS بناء على البناء وحده. يحتاج فحص Manage وفتح/إغلاق دليل الربط والاتصالات والبحث، بلغتين وبالمقاسات المتاحة، بعد توفير النسخة المعدلة.

## الفروق المتبقية والموانع

- المرجع يضم Google ومتاجر في جدول الحسابات. Channel API الحالي يعرض القنوات فقط؛ Google يبقى رابط تكامل فعلي في بطاقات الربط، ولا أُنشئ حسابات أو حالة اتصال وهمية له.
- Last Sync في المرجع يقابله Last check في Boat لأن المتاح دليل فحص اتصال لا وقت مزامنة بيانات. أهلية MM غير متاحة وتعرض — بوضوح.
- Disconnect في المرجع لا يساوي حذف القناة. لم يُعَد تسمية Delete إلى Disconnect؛ بقي الحذف داخل الإدارة بتأكيده الحالي.
- Manage في هذه الدفعة يفتح التفاصيل داخل الجدول؛ المرجع يذهب لصفحة إدارة خاصة بالمزود. لا ادعاء تطابق هذه الرحلة حتى فحص نماذج الربط التالية.
- فحوص Meta/WhatsApp/Telegram الخارجية وتغيير التوكينات/Webhooks ليست اختبارات مسموحة على البيانات الحقيقية؛ لم تُجرَ.

التعديلات الحالية لا تتطلب API جديدًا، لكن نشر رأس الفرع كله يجب أن يراعي دفعات إعدادات البوت المحفوظة سابقًا التي تحتاج API وmigration104 قبل Web. إعداد pre-deploy الحالي في Railway يطبق migrations؛ لا موارد أو متغيرات أو Sleep جديدة مطلوبة. حالة النشر الفعلية تُسجل بعد محاولة الاعتماد ولا تُستنتج من Git Push.
