# فصل النشر الاجتماعي ومطابقة مساراته

## مرجع تمت معاينته مباشرة
زيارة https://botsailor.com/social-post ثم Multimedia Post وقائمة المنشورات ونموذج Create دون حفظ أو نشر. المرجع يبدأ بثلاث بطاقات Multimedia / CTA / Carousel-Video، ثم قوائم منفصلة ونماذج إنشاء. قائمة Multimedia تحتوي النوع والصفحة والبحث وجدول Campaign ID / Name / Campaign Type / Publisher / Post Type / Actions / Status / Scheduled At / Error Message. النموذج يعرض اسم الحملة والنص والوسائط والتوقيت والمعاينة.

## التنفيذ
- فصل Social Posting عن CommercePanel: صفحة اختيار مستقلة، مسارا قائمة وإنشاء لكل نوع، ومعاينة محتوى فعلية محلية بدل Mock/JSON.
- حذف واجهة النشر الاجتماعي المكررة من التجارة، وطلب /commerce/social من ذلك المكوّن، والـCSS القديم الخاص بالبطاقات المحذوفة. النشر لم يعد يحمل المنتجات والمواعيد والعملاء والتكاملات غير اللازمة له.
- اسم الحملة وتصنيفها أصبحا محفوظين فعليًا، بترحيل 093 إضافي لا يحذف بيانات. القديم يصنف حسب النوع، والتصنيف الصريح لمنشورات الصور المتعددة ضمن Multimedia يبقى محفوظًا عند إعادة الترحيل.
- SocialService يحتفظ بالاسم والتصنيف عند تعديل من عميل قديم لا يرسلهما، ويحفظهما في مسودة إعادة المحاولة. التعديل متاح للمسودة فقط، والقنوات ما زالت مقيدة بالشركة وFacebook/Instagram.
- أنواع محتوى مستقلة: Text وLink وImage/Carousel وVideo، مع CTA وCarousel/Video ضمن مجموعتيهما، واختيار الحساب من القنوات المدعومة فقط. الروابط تحفظ كـtext+link طبقًا لمحرك النشر الموجود.
- قائمة المنشورات تحتوي البحث والنوع والصفحة والصفحات وأسماء الحملات والحالة الحقيقية، ومعاينة وتعديل المسودة وجدولة باستخدام API الحقيقي القائم. لا بيانات نجاح أو نشر وهمية، ولا نشر فعلي أثناء العمل.
- حذف عرض نتائج JSON في التجارة والمواعيد، وإظهار نتيجة إجراء مفهومة؛ فحص التوفر يوضح أن الحجز لم يُنشأ، ومعاينة المنتج تعرض نصه. إضافة مانع فوري لتكرار الطلبات.

## تنظيف الشريط المشترك
- إزالة قائمة Workspace Switcher الزائدة مقارنةً بالشريط في Dashboard وSettings وSocial Posting، وحذف مكوّنها غير المستخدم وCSS وطلبَي القراءة المكررين. لم يُحذف حساب أو عضوية ولم تتغير صلاحيات أو جلسة دخول.

## التحقق
- PostgreSQL بمستخدم NOBYPASSRLS: حفظ الاسم والتصنيف وتعديلهما، الاحتفاظ بهما مع العميل القديم وإعادة المحاولة، إعادة تشغيل migration دون تغيير تصنيف صريح، منع حساب الشركة الأخرى، رفض text على Instagram وتعديل غير المسودة، والتحقق من نوع تصنيف الحملة: ناجح.
- TypeScript وESLint وNext.js build كامل وAPI build وgit diff --check: ناجحة للنشر الاجتماعي؛ أُعيد بناء الواجهة بعد تنظيف الشريط المشترك.
- API: SUCCESS للنشر 64db9913-958f-4b08-b984-9b989a2b9854، commit 4c2e98537bcb227e156d3b46ce6d507cbd9a6c4c. السجل يؤكد تطبيق migration 093 بنجاح. Web قيد التحقق من النشر.
- محاولة فتح صفحة المستخدم مباشرة ما زالت تعيد إلى /login؛ لا فحص مرئي للنسخة داخل الحساب ولا تكرار لطلبات بيانات الدخول المعلقة سابقًا.

## حدود واضحة
ليست مطابقة كاملة لكل النظام أو النشر الاجتماعي: رفع الوسائط وReels وخيارات التكرار وتوقيت الحساب والنشر المتعدد للحسابات وFacebook carousel الأصلي ببطاقات مستقلة ما زالت تحتاج تنفيذًا. النظام الحالي يستخدم آلية نشر الصور المتعددة الموجودة لديه؛ لا يدّعي دعم حقول غير مطبقة. حفظ المسودة والجدولة منفصلان، ولا يتحول الحفظ إلى نشر تلقائي. القائمة الحالية تعرض أحدث 200 منشور وفق حد API السابق؛ توسيع التصفح من الخادم ما زال مطلوبًا. الحسابات والدفع وWebhook وبعض صفحات الأمان ومدير الباقات ما زالت غير مكتملة المطابقة، كما هو موثق في الدفعات السابقة.
